# CampaignManager 2.0 — план

Точка входа для сессий, которые делают 2.0. Порядок чтения: этот файл → своя задача в
[TASKS.md](TASKS.md) → нужные разделы [SCHEMA.md](SCHEMA.md) (схема и перенос данных) и
[AUDIT.md](AUDIT.md) (что и почему меняем — с доказательствами из кода и базы).

Составлен 2026-10-01 по коду `master` (`e9cd740`) и живой базе. Числа ниже — на эту дату. Номера
строк в AUDIT — на `e9cd740`. Влитое после (#85–#94: фильтры каталогов, плотные строки навыков,
ограничение владельца листа) план учитывает, но отдельно не перепроверялось.

## Зачем

v1 вырос до ~70 тыс. строк без миграций (C# 27,6k, Razor 35,9k, CSS 5,2k, JS 1,2k) и упёрся
в три вещи:

1. **Схема держит правила в комментариях, а не в базе.** «Ровно один владелец листа» оказался
   нарушен в 7 из 54 листов (ограничение добавили в v1 только по итогам аудита, #91). Сценарий —
   одна строка с пятью JSONB, и связи в нём висят без контроля.
   Человек везде записан строкой с почтой. Справочники связаны по имени, отсюда целый класс
   ошибок. Подробности — AUDIT, «Данные».
2. **Blazor Server на iPad хрупок.** Заметная часть кода и документации — сохранение circuit на
   паузе, восстановление после обрыва, снимки пререндера, состояние в адресе «чтобы пережить
   паузу». Всё это лечит модель хостинга, а не делает работу.
3. **Один и тот же код написан несколько раз**: семь каталогов, два движка сцен (бой и погоня),
   три генератора листа. Оценки по областям — в AUDIT.

Активных пользователей нет, поэтому переходим чисто: новая схема, перенос данных с отбрасыванием
мусора, новая структура решения. Сломанное можно потерять.

## Что должно получиться

- **Те же возможности**, кроме явно снятых (D6). Список маршрутов и сценариев для сверки —
  «Паритет» ниже.
- **Веб** — Blazor WebAssembly поверх HTTP API. Сервер без состояния: деплой и обрыв связи
  не сбрасывают экран Хранителя.
- **Мобильное приложение** (позже) — Avalonia поверх того же API. Общие с вебом: правила книги
  и типы документов (`Core`), контракты API (`Contracts`), типизированный клиент (`ApiClient`).
  UI у приложения свой.
- **База** — схема `cm` по SCHEMA.md; инварианты держит база.
- **Тесты**: правила книги — юнит-тестами (до переноса кода), API — интеграционными на Postgres.
- **Кода меньше, и он единообразен**: один каталог вместо семи, одно ядро сцены, один конструктор
  листа, одна модель прав. Объём: **≈50 тыс. строк вместо ≈70 тыс. (−30%)**, и это вместе с новым
  слоем API. Половина уходит только в справочниках. Главный выигрыш — исчезают целые классы
  ошибок (AUDIT, «Итог»).

## Архитектура

```
src/
  CampaignManager.Core/        чистый C#: документы (лист, статблок, сцена), правила книги, кости,
                               разбор формул, таблицы. Без EF, ASP.NET, Blazor, HTTP. Безопасен для
                               AOT и обрезки: JSON только через source-generated контексты.
  CampaignManager.Contracts/   DTO и интерфейсы API по модулям (ICampaignsApi, ICharactersApi, …).
                               Тоже без зависимостей от платформы.
  CampaignManager.ApiClient/   HttpClient-реализации интерфейсов Contracts. Им пользуются веб,
                               мобильное приложение и интеграционные тесты.
  CampaignManager.Data/        EF Core: CmDbContext, конфигурации, миграции схемы cm.
  CampaignManager.Server/      ASP.NET Core: минимальные API по модулям (/api/v1/…), прикладные
                               сервисы, права, Auth0 (cookie для веба, JWT для приложения), MinIO,
                               хост WebAssembly, статические страницы (вход, второй экран раздатки).
  CampaignManager.UI/          Razor-компоненты и страницы, дизайн-система (Tailwind), JS-модули.
                               Ходит только в интерфейсы Contracts и в Core.
  CampaignManager.Web.Client/  хост WebAssembly: регистрирует ApiClient и AuthenticationStateProvider.
tests/
  CampaignManager.Core.Tests/    правила книги
  CampaignManager.Server.Tests/  API на настоящем Postgres через ApiClient
  CampaignManager.UI.Tests/      UI-кит на bUnit
tools/
  CampaignManager.Migrate/       перенос v1 → v2 (SCHEMA.md, «Перенос данных»)
mobile/ (позже)
  CampaignManager.Mobile/        Avalonia: Core + Contracts + ApiClient, свой UI
```

### Зависимости между проектами

`Core` ← `Contracts` ← `ApiClient` ← `Web.Client`, мобильное приложение.
`Core` + `Contracts` ← `UI` ← `Web.Client`.
`Core` + `Contracts` + `Data` ← `Server` (он же ссылается на `UI` и `Web.Client`, чтобы отдать
приложение). `Data` ← `Migrate`.

Запрещено: `UI` → `Data`/`Server`, `Core` → что угодно, кроме BCL. Проверяет тест на архитектуру
в `Server.Tests` (через рефлексию по ссылкам сборок).

### Модули

Нарезка вертикальная, как в v1. Модуль — папка с одним именем в каждом проекте:
`Identity`, `Files`, `Campaigns`, `Characters`, `Scenarios`, `Catalogs`, `Encounters`, `Checks`,
`KeeperScreen`, `Music`, `Admin`, `Profile`. У модуля в `Server` — расширения
`AddXxxModule(services)` и `MapXxxApi(app)`; `Program.cs` их только перечисляет. У модуля в `UI` —
свой `CLAUDE.md` с перенесённым знанием v1 (см. «Правила для сессий»).

### Принципы

- **API — единственный путь к данным**, и для веба, и для приложения. Прикладной сервис на
  сервере принимает и отдаёт DTO из `Contracts`, эндпоинт его только вызывает.
- **Права — один модуль** (`Server/Access`): scoped `AccessPolicy` с методами по ресурсам
  (кампания, прохождение, лист, сценарий, раздатка, справочник, админка). Методы возвращают
  `CanRead`/`CanEdit`/`CanDelete`, а `Demand…` бросает исключение. Правил около десятка, поэтому
  обработчик `IAuthorizationService` на каждый ресурс — лишняя церемония; две ролевые политики
  остаются для `[Authorize]`. **Каждый метод записи прикладного сервиса** зовёт `Demand…` — в v1
  четыре сервиса справочников не проверяли права вовсе. В DTO уходят флаги, посчитанные той же
  `AccessPolicy`: UI по ним прячет кнопки, но защитой это не считается.
- **DbContext на запрос** (scoped). `IDbContextFactory` в v1 был нужен из-за circuit, в API —
  нет.
- **Конкурентность**: `xmin` → ETag, `If-Match` на запись, 409 при конфликте. UI показывает
  «изменено на другом устройстве» и предлагает перечитать.
- **Документы** (лист, статблок, сцена) — типы `Core`. Неизвестные поля переживают чтение и запись
  (`[JsonExtensionData]`): старая версия приложения не должна стирать то, чего не знает.
  Версия документа — в колонке, апкастер — в `Core`.
- **Версия API** — `/api/v1`, совместимость только наращиванием. Приложение из App Store
  обновляется с опозданием, и сломанный контракт сломает его у игроков.
- **Состояние клиента** живёт в браузере. Несохранённая правка листа — черновик в
  `localStorage`, а не `[PersistentState]`; открытая вкладка, раздел или локация — в адресе,
  чтобы на неё можно было дать ссылку.
- **Кости и уровни успеха** — модуль `Core/Dice` (в v1 — статические методы `CombatService`,
  которыми пользуется всё приложение).
- **Тексты UI** — на русском, как в v1. Культура WebAssembly — `ru-RU`.

## Правила для сессий

- **Одна задача — одна сессия — один PR** (или стек, если в задаче несколько слоёв; правила
  `gh stack` — в корневом `CLAUDE.md`). Задачи одной волны независимы и идут параллельно от
  `master`.
- **Готово** = `dotnet build` без предупреждений + `dotnet test` зелёный + проверка в браузере
  на iPad (1366×1024 и 1024×1366) и, для страниц игрока, на iPhone (390×844) + обновлён `CLAUDE.md`
  модуля + отмечены пункты паритета.
- **v1 заморожен**: только исправления того, что мешает играть. Новые функции — сразу в 2.0.
- **В боевую базу не пишем.** Работа идёт на ветке Neon `dev`; `cm` наполняется переносом
  (`T1.3`), прод трогает только `T3.2` — и только руками владельца.
- **Знание переносим, обходы — нет.** Из `CLAUDE.md` фич v1 в `CLAUDE.md` модуля 2.0 переезжают
  правила книги, уроки вёрстки под iPad и продуктовые решения. Заметки про circuit, пререндер,
  `IDbContextFactory`, ручные сбросы кэша и совместимость со старым JSONB не переезжают.
- **Правило «одна копия формулы»** из v1 остаётся: любая формула книги живёт в одном месте `Core`
  и покрыта тестом.
