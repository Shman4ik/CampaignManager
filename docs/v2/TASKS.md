Правила работы со схемой — [src/CLAUDE.md](../../src/CLAUDE.md), «База». Отличия от карточки:

  `Era`, `Characteristic`, `Difficulty` — в корне `Core`: если T1.7 заведёт свои, оставить одну копию;
- `DataProtectionKey` — стандартная сущность пакета, `CmDbContext` реализует `IDataProtectionKeyContext`;
- defaults в DDL есть, но EF их не использует (`HasDbDefault`): иначе «нулевое» значение подменялось бы
  default'ом базы;
- расхождения миграции с текстом DDL (CHECK у `eras`, индексы на FK, `xmin` у `music_tracks`) записаны
  в SCHEMA.md под «DDL».

**Зависит от:** T1.1, T0.1, D3.

**Шаги.**
1. Сущности и конфигурации по модулям; `UseSnakeCaseNamingConvention()`; схема по умолчанию `cm`,
   журнал миграций — `cm.__ef_migrations_history` (не общий `public`, на котором v1 уже обжёгся).
2. Хелпер: CHECK для перечисления генерируется из самого enum.

6. `dotnet ef migrations script` → сверить с DDL в SCHEMA.md. Расхождение исправляется в коде

**Готово, когда** миграция применяется на пустой базе и на ветке `dev`; `Server.Tests` поднимают

### T1.4 — Вход, пользователи, права

**Сделано 2026-10-02.** `Server/Identity`: OIDC + кука как в v1 (`email_verified`, белый список,
`AdminEmails`, `ResponseMode = Query`, автовход через Google, выход гасит сессию Auth0), JWT Bearer
второй схемой под policy scheme, пользователь заводится и привязывается при входе (`UserDirectory`:
sub, затем почта), `GET /api/v1/me`. `Server/Access`: `CurrentUser` (роль из `cm.users` на запрос),
`AccessPolicy` по всей карте прав, `Demand` → 404/403 ProblemDetails, политики `Keeper`/`Admin` для
`[Authorize]`. Клиент: `MeAuthenticationStateProvider`, `/login`, меню пользователя, `AuthorizeRouteView`.
`Server.Tests`: каждое правило карты прав (`AccessPolicyTests`), вход/выход/автовход до редиректа на
Auth0, привязка по почте, роль без кэша, закрытость каждого эндпоинта `/api/v1`. Знание —
[Identity/CLAUDE.md](../../src/CampaignManager.Server/Identity/CLAUDE.md),
[Access/CLAUDE.md](../../src/CampaignManager.Server/Access/CLAUDE.md). Отличия от карточки:
- вход целиком на dev-приложении не пройден агентом: на localhost Auth0 всегда спрашивает согласие,
  а принимать его — решение человека. Проверено до экрана согласия (автовход через Google без кликов)
  и отказ на нём; остальное — паритет, пункт 1;
- JWT подключён, но **без API (audience) и Action в тенанте не работает** — заводит владелец
  (вопрос в PR); почту в токен кладёт Action под `https://cthulhu.dmnet.dev/`;
- админ может всё (в v1 не правил чужие кампании), кампанию создаёт только Хранитель, снять бронь —
  только Хранитель этой кампании, НПС игроку не виден — список в Access/CLAUDE.md;
- игрок не может править справочник прямым запросом — проверено на `AccessPolicy` (`ForCatalogAsync`
  + `Demand` → 403); эндпоинтов справочников ещё нет, их делает T2.1 с `Demand` в каждом методе записи;
- заглушка прав T1.5 (`FileAccessStub`) заменена на `AccessPolicy.ForFilesAsync`: читать и загружать —
  вошедший, сироты — админ (`Policies.Admin`); `uploaded_by_id` — из `CurrentUser`; загрузка без
  antiforgery закрыта `SameSite=Lax` куки входа (межсайтовый POST приходит анонимным — 401);
- ни одной миграции: `users` и `campaign_members` из T1.2 хватило;
- ключи Data Protection — в `cm.data_protection_keys` с именем приложения v1 (куки переживут переключение).

**Цель.** Auth0 и модель прав 2.0. Знание v1 — корневой `CLAUDE.md`, «Authentication (Auth0)»;
карта прав — AUDIT, «Права».

**Зависит от:** T1.2.

**Шаги.**
1. OIDC + своя кука, как в v1: `email_verified` обязателен, белый список,
   `ResponseMode = Query`, автовход через Google по куке последнего способа, выход гасит сессию
   Auth0. Пользователь создаётся при входе: поиск по `auth0_sub`, затем по email (так связываются
   перенесённые пользователи).
2. Роль — из `users`; кэш на запрос, без `UserClaimsCache` на 5 минут: в WebAssembly клиент
   спрашивает `/api/v1/me`, а не трансформирует claims на каждый запрос статики.
3. Вторая схема — JWT Bearer (Auth0, PKCE) для мобильного приложения. Политики принимают обе.
4. `Server/Access`: `CurrentUser` (id, роль, email — один раз на запрос) и `AccessPolicy` с
   методами по ресурсам по карте прав AUDIT («Права»): `For(resource)` → флаги, `Demand…` →
   исключение → 403/404. Членство в кампании — один `EXISTS` по `campaign_members`.
   Флаги `canEdit`/`canDelete` в DTO считает она же.
5. Клиент: `AuthenticationStateProvider` на `/api/v1/me`, вход и выход — переходом на сервер.

**Готово, когда** вход и выход работают на dev-приложении Auth0; `Server.Tests` проверяют каждое
правило карты прав; игрок не может править справочник ни через UI, ни прямым запросом к API.

**Не потерять:** «нет объекта» и «нет доступа» для чужого листа и журнала неразличимы (404).

### T1.5 — Файлы

**Сделано 2026-10-02.** Модуль `Files` во всех слоях: `Contracts/Files` (маршруты, DTO, `IFilesApi`),
`FilesApiClient`, `Server/Files` (загрузка с дедупликацией по sha256, `GET|HEAD /api/v1/files/{id}`
со своего origin, Range потоком, `immutable` + `ETag`, 304, внешние адреса — 302, отчёт и удаление
сирот), один клиент MinIO на приложение без таймаута и без `BucketExists`. Миграции нет — хватило
таблицы T1.2. Проверено: картинка и mp3 загружаются и отдаются; на 1366×1024 и 1024×1366 перемотка
40-мегабайтного трека на 900 с буферизует только отрезок вокруг точки (Range), Web Audio после
перемотки слышит сигнал. Знание — [Server/Files/CLAUDE.md](../../src/CampaignManager.Server/Files/CLAUDE.md).
Отличия от карточки:
- проверка в браузере — Chromium с вьюпортом iPad, не Safari; форму `bytes=0-1`, которой Safari
  узнаёт размер, покрывает тест. Живой Safari на iPad — за владельцем (или T2.8);
- права — заглушка `FileAccessStub` (Development/Testing — можно, иначе 403) с TODO на T1.4;
  `uploaded_by_id` пока не заполняется;
- «удаление отдельной кнопкой» — на dev-странице `/dev/files`; экран админки — T2.9;
- ключ объекта — `<images|music>/<sha256><расширение>`, а не случайный GUID v1: уникальный
  `storage_key` гасит гонку двух одинаковых загрузок;
- сирота — только старше `Files:OrphanGracePeriod` (сутки), список ссылок для anti-join строится
  по модели EF, удаление повторяет условие в самом `DELETE`;
- SVG не принимается (документ со скриптами на нашем origin); ответ на Range не режется по 4 МиБ —
  он поток, а не буфер;
- `IObjectStorage`: тесты API идут на хранилище в памяти (в CI нет MinIO), адаптер MinIO — отдельными
  тестами по `CM_TEST_MINIO`;
- настроек MinIO в `appsettings.json` нет: у v1 dev и прод — один бакет, отдельного dev-бакета нет
  (вопрос владельцу в PR). Локальная проверка — MinIO в wslc; образа `minio/minio` на Docker Hub
  больше нет, взят `cgr.dev/chainguard/minio`.

**Цель.** Модуль `Files` поверх MinIO и таблицы `cm.files`.

**Зависит от:** T1.2.

**Шаги.**
1. **Загрузка:** multipart и sha256 — повторный файл не плодит объект.
2. **Отдача** — одним `GET /api/v1/files/{id}`, **со своего origin и с поддержкой Range**. Это
   требование Web Audio на iPad, см. `Music/CLAUDE.md` v1 про `/api/minio/audio`.
   - Стриминг, а не буфер в `MemoryStream`.
   - `Cache-Control: immutable` и `ETag`: ключи неизменяемы.
3. **Клиент MinIO** — один на приложение. Без `BucketExists` перед каждой загрузкой и без
   стандартного resilience-обработчика с таймаутом 10 с: длинный трек он оборвёт.
4. **Внешние адреса** — строки `files` с `external_url`.
5. **Админский эндпоинт «сироты»** (anti-join из SCHEMA): сначала отчёт, удаление — отдельной
   кнопкой.

**Готово, когда** картинка и mp3 загружаются и отдаются; перемотка трека работает в Safari на
iPad-вьюпорте.

   - `cm-page`.

6. **Индикатор связи и сохранения** для вызовов API — вместо диалога переподключения circuit.
7. **JS — ES-модули** через `IJSObjectReference`, без глобальных скриптов и `eval`.
8. **Страница `/dev/ui`** (только в Development): все компоненты на одном экране.

### T2.1 — Справочники

**Цель.** Один обобщённый каталог вместо семи ручных: 15,4 тыс. → ~7,7 тыс. строк (AUDIT,
«Справочники»).

**Входы.** AUDIT, «Справочники»; `CLAUDE.md` фич Weapons, Items, Spells, Books, Skills, Bestiary;
в `Characters/CLAUDE.md` — раздел про `/occupations`.

**Шаги.**
1. **Сервер.** Общий сервис каталога: чтение списка целиком с `ETag` (справочники маленькие —
   до 312 строк), запись только через `AccessPolicy.DemandCatalogEdit`. Дубль имени — 409 с
   понятным текстом, а не молча закрытая модалка.
2. **Клиент.** Список грузится один раз, поиск, фильтры и страницы — на клиенте; у всех каталогов
   одинаково. В v1 счётчик брали из базы, а строки из кэша.
3. **`CatalogPage<T>` + `CatalogDefinition<T>`:**
   - колонки, сортировки, фильтры (поиск, enum, эпоха, флажки);
   - «колонка прячется, когда фильтр фиксирует её значение»;
   - `CanExpand`, порог таблицы (замерить по числу колонок, как в v1), форма, флаги прав.
   - Вид «таблица + карточки»; бестиарий — вид «галерея» (`?open=`).
4. **Описания каталогов:** навыки (детали навыка — один компонент, им же пользуется справка на
   листе), профессии (редактор слотов по `occupation_slots`), оружие (подсказки разбора и
   `UnparsedMark`), предметы, заклинания, книги (связь с заклинаниями через `book_spells`).
5. **Бестиарий:** форма статблока по документу `statblock`, картинки через `files`, импорт и
   экспорт JSON.
6. **Обмен JSON** — общий `CatalogExchange`: ключ `code`, иначе имя; пропуск или перезапись;
   пробный прогон; одна пара модалок. Им же потом пользуются фонотека и сценарии.
7. **«Синхронизировать с правилами»** (профессии и остальное, где есть сид) — апсерт по `code`:
   ключ — код из таблицы `Core/Catalogs/*Codes`, запись с таким кодом обновляется (имя тоже — коды не
   меняются, имена могут), без него — создаётся; записи с `code` null (самодельные) синхронизация не
   трогает. Сид без текстов книги (D5): названия, коды, числа.
8. **История правок:** интерфейс не переносится (D6.1, подтверждено); снимок «после» пишет
   перехватчик.
9. **F-P13 — исправить** (решение владельца 2026-10-02, [rules-findings.md](rules-findings.md)):
   «Шок» и другой эффект без костей не считать разобранной формулой урона (`DamageFormulaParser`) —
   строка остаётся текстом, как обещают комментарии; поменять ожидание теста с `finding` F-P13.

**Готово, когда** все страницы справочников на iPad-вьюпортах; игрок не видит кнопок правки, а
прямой запрос на запись получает 403; эпоха, поиск, пагинация и кнопки строк одинаковы во всех
каталогах.

**Не потерять:** AUDIT, «Справочники → Не потерять» — правила таблицы XVII и статблока, замеры
вёрстки под iPad.

### T2.2 — Кампании, участники, журнал, главная

### T2.3 — Лист сыщика

**Цель.** Страница листа на документе 2.0. Самая насыщенная знанием часть приложения.

**Зависит от:** по умолчанию + T2.1 (поиск по справочникам), T2.7 (диалог проверки и трата Удачи).

**Входы.** AUDIT, «Персонажи и НПС»; `Characters/CLAUDE.md` v1 целиком — раскладка листа, рассудок
и безумие, книги Мифов, фаза развития, сохранение.

**Шаги.**
1. **API.** Чтение листа (документ + `ETag`), запись с `If-Match` (409 при конфликте), портрет
   через `files`. Права — `AccessPolicy`: владелец-игрок и Хранитель его кампании; «нет листа» и
   «нет доступа» — одинаковый 404.
2. **Секции листа — из списка описаний.** Меню секций строится по тому же списку (в v1 меню было
   написано дважды и без «Рассудка»).
3. **Одна разметка на одну вещь:**
   - `SkillRow` вместо трёх копий;
   - `CatalogSearch<T>` вместо шести;
   - оружие — одна разметка для таблицы и карточек;
   - биография — по таблице описаний граф.
4. **Правила из разметки — в `Core`:** операции `SanityPanel`, привыкание, стадия книги Мифов,
   «Средства» в фазе развития. Вычисляемое на листе — только для чтения (в v1 его можно было
   править, и пересчёт молча затирал правку).
5. **Удача тратится в одном месте** — общий диалог проверки (T2.7). `LuckSpendModal` с
   противоположной логикой снятия отметки уходит (D6.5).
6. **Автосохранение.**
   - Изменился слепок документа → запись с `If-Match`.
   - Общий флаг занятости с кнопкой «Сохранить»; одно уведомление на серию ошибок; значок
     состояния.
   - При конфликте — «лист изменён на другом устройстве: перечитать?».
   - Черновик несохранённого — в `localStorage`, плашка о восстановлении — только если черновик
     расходится с базой.
7. **Исправить ошибки v1** из AUDIT («Персонажи и НПС → Ошибки»): заклинание с листа меняло
   справочник; бой не видел правку оружия; навык из справочника получал 0; «Сохранить» затирало
   имя игрока.
8. **Спросить владельца** до начала: сливать ли «Предысторию» с «Заметками»; что делать с графами
   «Фобии» и «Магические предметы» при наличии структурированных записей.

**Готово, когда** проходят сценарии паритета 3 и 4, а правка одного листа с двух устройств даёт
второму сообщение о конфликте, а не молчаливую перезапись.

**Не потерять:** AUDIT, «Персонажи и НПС → Не потерять» — вёрстка под iPad (`@key`, тап-цели,
`@container`, подписи над полями), правила рассудка, книг Мифов и фазы развития.

  предметы, состав НПС, прегены.
- Каждая вложенная сущность — своя строка и свой запрос: правка одной вкладки не затирает другую
  (в v1 так терялись правки).
- Модалки декларативные (`IsVisible`), без `@ref` + `Show()`; выбор из каталога — общий
  `CatalogPickerModal<T>`.
- Права — по `AccessPolicy`, флаги приходят в DTO.

**T2.5b — Режим игры и раздатки.**
- Режим игры в адресе: `?mode=play&location=&handout=`, переходы с `replace: true`.
- Проверки локации открывают общий диалог проверки (T2.7) по сыщикам кампании **прохождения**.
- «Показать игрокам» и второй экран `/scenarios/{id}/handouts/{handoutId}` — статическая страница
  сервера, без интерактива.
- `keeper_note` не попадает ни в показ, ни на второй экран.
- Музыка локации — теги и прибитые треки (T2.8).

**T2.5c — Прохождения и ваншоты.** `RunService`:
- «играть в кампании» — прохождение без копии содержимого;
- «объявить ваншот» — одной транзакцией кампания `OneShot`, Хранитель-участник, прохождение с
  `signup_open`;
- бронь — копия листа прегена игроку (`origin_character_id`) плюс строка `run_reservations`;
  повтор и чужая бронь отсекаются ключами;
- снять бронь может игрок или ведущий прохождения, а не любой Хранитель;
- анонс правится в одной форме прохождения.

**T2.5d — Импорт и экспорт JSON.**
- Формат v1 сохраняется: без id, родитель по имени, НПС из библиотеки по имени, навыки без
  учёта регистра и «ё».
- Импорт — одна транзакция.
- Экспорт отдаёт и то, что v1 терял: тварей, предметы, прегенов, музыку локаций.
- Анонс в формат больше не входит — он у прохождения.
- Обновить скилл `scenario-import` под 2.0.

**Готово, когда** проходят сценарии паритета 5 и 6.

### T2.6 — Сцены: бой и погоня

сценария), T2.7.

**Входы.** AUDIT, «Сцены»; `Combat/CLAUDE.md`, `Chase/CLAUDE.md` v1. Правила (без UI)
переносятся на тестах T0.2. Ошибки из списка AUDIT чинятся здесь с правкой ожиданий тестов и
записью в `rules-findings.md`.

**T2.6a — Ядро сцены.** `Core/Encounters`:
- участник — ссылка на лист или тварь плюс снимок чисел; id участника ≠ id листа;
- очередь по id активного участника;
- типизированный журнал;
- **резолв возвращает эффекты, применяет их один `Apply`**, «Отменить» — выбросить эффекты;
- состояние — `encounters.state` с версией, автосохранение через API с `ETag`.

**Применение пишет в лист**: ПЗ, рассудок, ПМ, МОЩ, привыкание. В v1 итог боя в лист не попадал.

Общий UI: `ParticipantPicker`, `ParticipantSelect`, `ParticipantRow` со `StatBar`, `EncounterLog`,

**T2.6c — Погоня.** Трасса, СКО и действия перемещения, помехи и преграды, транспорт, часть 5 —

## Волна M. Мобильное

### M1 — PWA

**Цель.** Веб ставится на экран «Домой» iPad и iPhone и открывается как приложение.

**Зависит от:** T3.2 (можно и раньше, на 2.0 до переключения).

**Шаги.** Манифест, иконки (включая `apple-touch-icon`), `apple-mobile-web-app-*`, service worker

**Готово, когда** установленное с экрана «Домой» приложение на iPad открывается без адресной
строки, а после деплоя предлагает обновиться.

### M2 — Раскладки для телефона

**Цель.** Игрок пользуется 2.0 с iPhone: главная, свой лист (просмотр и правка), помощник
создания, проверки и кости, журнал кампании, раздатки.

**Зависит от:** T2.2, T2.3, T2.4, T2.5, T2.7.

**Шаги.** Вьюпорт 390×844 (и 430×932). Экраны Хранителя (сценарий, бой, погоня) на телефоне не
обязаны быть удобными, но не ломаются и не прокручиваются вбок.

### M3 — Живой стол

**Цель.** Хранитель показывает раздатку — она появляется на телефонах игроков. Изменения листа и
сцены видны на других устройствах без перезагрузки.

**Зависит от:** T2.3, T2.5, T2.6.

**Шаги.** SignalR-хаб `TableHub` на сервере (группы по кампании), события «раздатка показана»,

приложение. Второй экран раздатки (`/scenarios/{id}/handouts/{handoutId}`) остаётся статической
страницей — телевизору у стола хаб не нужен.

### M4 — Приложение на Avalonia

**Цель.** Нативное приложение для iPhone и iPad на том же API (D4).

**Зависит от:** T3.2, M3 (по желанию).

**Шаги.**
1. `mobile/CampaignManager.Mobile` (Avalonia, iOS; Android — по желанию) на `Core` + `Contracts` +
   `ApiClient`. UI свой, на XAML; начать со сценариев игрока из M2, а не со всего приложения.
2. Вход — Auth0 для нативного приложения (PKCE, системный браузер через

3. Проверить `Core`/`Contracts`/`ApiClient` под AOT на iOS — именно ради этого они с T1.1

4. CI: `macos-latest` (публичный репозиторий — бесплатно), подпись и TestFlight — аккаунт Apple
   Developer владельца.

**Готово, когда** игрок входит с iPhone, видит свой лист, бросает проверку и получает раздатку.
