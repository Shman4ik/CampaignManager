# Admin (Server) — пользователи, роли, заявки

Модуль T2.9: `AdminModule` (`AddAdminModule`/`MapAdminApi`), `AdminService`. Маршруты, DTO и `IAdminApi` —
`Contracts/Admin`, клиент — `ApiClient/Admin`, страницы — [UI/Admin/CLAUDE.md](../../CampaignManager.UI/Admin/CLAUDE.md).
Знание перенесено из `Features/Admin/CLAUDE.md` v1. Сироты файлов — тоже админка, но их API живёт в модуле
[Files](../Files/CLAUDE.md) (`/api/v1/admin/files/orphans`), здесь только страница.

## API

Группа — `RequireAuthorization(Policies.Admin)`, и **каждый метод сервиса ещё раз** зовёт
`AccessPolicy.CanAdministerAsync().Demand()` (в v1 — `EnsureAdministratorAsync`): атрибут страницы и политика
эндпоинта — удобство, граница — сервис.

| Метод и адрес | Что |
|---|---|
| `GET /api/v1/admin/summary` | `PendingApplications` — счётчик у пункта меню «Заявки» |
| `GET /api/v1/admin/users` | все пользователи по почте (их десятки — поиск и страницы на клиенте) |
| `PUT /api/v1/admin/users/{id}/role` | `{ role }` — сменить роль |
| `GET /api/v1/admin/keeper-applications?status=` | заявки, новые сверху; без `status` — все |
| `POST /api/v1/admin/keeper-applications/{id}/approve` | одобрить |
| `POST /api/v1/admin/keeper-applications/{id}/reject` | `{ comment }` — отклонить |

404 — нет пользователя или заявки, 409 (`ApiProblemException.Conflict`, код `conflict`) — заявка уже рассмотрена
или это последний администратор, 400 (`invalid`) — форма.
**Почта в ответах админки есть** (в отличие от остальных модулей): администратор различает людей по ней — имена
совпадают и бывают равны почте.

## Роли

- Роль читается из `cm.users` **на каждый запрос** (`CurrentUser`): смена видна человеку со следующего запроса.
  В v1 после смены роли надо было сбрасывать `UserClaimsCache` (5 минут) — его больше нет.
- **Администратор может всё** (решение владельца), в том числе снять роль с себя. Но **последнего администратора не
  понизить** (409): иначе админку открыть некому, кроме `Authorization:AdminEmails` при следующем входе.
- Роли в UI — по-русски и одними цветами в кабинете и админке (`UI/Identity/RoleLabels`); в API — имена членов
  `UserRole` (`Player`/`Keeper`/`Admin`).

## Заявки

- **Одобрение — одна транзакция**: статус заявки, кто и когда рассмотрел, и роль. В v1 статус писался в `games`, а
  роль — в `identity` другим контекстом, и сбой между ними оставлял одобренную заявку без роли. На ветке `dev` такая
  есть и сейчас (перенесена из v1: «Одобрена», а человек — игрок). Тест `Failed_role_update_rolls_back_the_approval`
  роняет запись роли триггером и проверяет, что заявка осталась «ожидает».
- Рассмотреть можно только заявку «ожидает»: условие стоит **в самом `UPDATE`**, поэтому две вкладки или два
  администратора не рассмотрят её дважды — второму 409.
- Роль при одобрении **только повышается**: `Player → Keeper`; Хранитель и администратор остаются собой (в v1
  одобрение ставило `GameMaster` всем подряд — администратора бы понизило).
- Отказ роль не трогает; комментарий (до 1000 символов) видит подавший в кабинете и может подать снова.
- `updated_at` при `ExecuteUpdate` ставится руками: перехватчик меток времени видит только `SaveChanges`.
