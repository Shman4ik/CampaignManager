# Access — права

Один модуль на все права 2.0 (README, «Принципы»). Вход и пользователи — [Identity](../Identity/CLAUDE.md).

## Как пользоваться

- **`CurrentUser`** (scoped) — кто делает запрос: `SignedInUser(Id, Email, DisplayName, Role)` из
  `cm.users`, один запрос к базе на HTTP-запрос. `IsKeeper` — Хранитель **или** администратор.
- **`AccessPolicy`** (scoped) — все правила. `For…Async(id)` → `Access(CanRead, CanEdit, CanDelete)`,
  `Can…Async()` → `bool` для действий без объекта (создать, вступить, начать сцену, админка).
- **Каждый метод записи прикладного сервиса** зовёт `Demand`:
  `await access.ForCharacterAsync(id, ct).Demand(Operation.Edit);` /
  `await access.CanCreateScenarioAsync(ct).Demand();`. В v1 четыре справочника не проверяли права
  вовсе — `[Authorize]` на странице защитой не считается.
- **Флаги в DTO** (`canEdit`/`canDelete`) — из того же `Access`; UI по ним прячет кнопки. Для списков —
  статические `ForCampaign(user, role)` / `ForMember(…)` по уже прочитанной строке: правило то же, запроса
  на строку нет.
- **Отказ:** объект не виден (или его нет) — `AccessDeniedException` с **404**, виден, но нельзя —
  **403**; без объекта (`Can…`) — 403. `AccessExceptionHandler` превращает это в ProblemDetails.
  «Нет такого листа» и «чужой лист» неразличимы — перебирать нельзя.
- **Эндпоинты API закрыты по умолчанию**: группа модуля — `.RequireAuthorization()` (политика по
  умолчанию — вошёл и есть в `cm.users`) или `RequireAuthorization(Policies.Keeper|Admin)`.
  Тест `Every_api_endpoint_requires_authorization` падает на открытый эндпоинт; анонимный —
  только добавив его в список теста, с причиной.
- Роль в политиках — `UserRequirementHandler` через `CurrentUser`, не `RequireRole`: в куке роли нет.

## Правила

Администратор может всё, но несуществующий объект и ему — 404. «Хранитель» — роль платформы, а не
право на чужую кампанию: там решает строка `campaign_members` с ролью `Keeper`.

### Отличия от v1 (намеренные)

- снять бронь прегена может Хранитель **этой** кампании, а не любой;
- преген и НПС в чужую кампанию или сценарий кампании не положить (была дыра `CopyPregenToScenarioAsync`
  и `CreateCharacterAsync`); сценарии в 2.0 — общая библиотека, привязка к кампании — прохождение;
- создать кампанию может только Хранитель по роли (в v1 — кто угодно);
- администратор правит и чужие кампании (в v1 — нет, хотя журнал правил);
- НПС игроку не виден (в v1 «ничейный» лист читали все — из-за модели, а не по решению);
- справочники, фонотека и чтение сценария проверяются на сервере (в v1 — нет). Справочники — каждый
  метод записи `CatalogService` (T2.1, [Catalogs/CLAUDE.md](../Catalogs/CLAUDE.md)).

схемой `cm`. Новое правило — строка в таблицу выше и тест туда же.
