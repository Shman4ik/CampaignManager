# Campaigns (Server) — кампании, участники, журнал, главная

Модуль T2.2: `CampaignsModule` (`AddCampaignsModule`/`MapCampaignsApi`), сервисы `CampaignService`,
`JournalService`, `HomeService`. Маршруты, DTO и `ICampaignsApi` — `Contracts/Campaigns`, клиент —
`ApiClient/Campaigns`, страницы — [UI/Campaigns/CLAUDE.md](../../CampaignManager.UI/Campaigns/CLAUDE.md).
Таблицы — `campaigns`, `campaign_members`, `campaign_sessions` (+ чтение `scenario_runs`,
`run_reservations`, `characters`) из T1.2; миграций модуль не добавил.

## API

| Метод и адрес | Что | Права (`AccessPolicy`) |
|---|---|---|
| `GET /api/v1/home` | главная одним запросом | вошедший |
| `GET /api/v1/campaigns` | мои кампании (админу — все) | вошедший |
| `POST /api/v1/campaigns` | создать; создатель — участник-Хранитель | `CanCreateCampaignAsync` — Хранитель по роли |
| `GET /api/v1/campaigns/{id}` | кампания и участники | `ForCampaignAsync` Read |
| `PUT /api/v1/campaigns/{id}` | одна форма: имя, вид, статус, эпоха | `ForCampaignAsync` Edit |
| `DELETE /api/v1/campaigns/{id}` | удалить | `ForCampaignAsync` Delete |
| `POST /api/v1/campaigns/{id}/join` | вступить с псевдонимом | `CanJoinCampaignAsync` |
| `PUT /api/v1/campaigns/{id}/members/{userId}` | псевдоним | `ForMemberAsync` Edit |
| `DELETE /api/v1/campaigns/{id}/members/{userId}` | выйти / исключить игрока | `ForMemberAsync` Delete |
| `GET/POST /api/v1/campaigns/{id}/journal` | журнал / новая встреча | `ForCampaignAsync` Read / Edit |
| `PUT/DELETE /api/v1/campaigns/{id}/journal/{sessionId}` | правка / удаление встречи | `ForCampaignAsync` Edit / Delete |

Ответы: 404 — кампании нет **или она не видна** (неразличимо: перебирать чужие журналы нельзя), 403 —
видна, но нельзя (в том числе вступить второй раз или в завершённую), 400 — форма, 409 — убрать
Хранителя или гонка двух вступлений. Смысловые отказы — `ApiProblemException.Invalid` (400) и
`.Conflict` (409, код `conflict`) из Platform (до T2.9 — свой `CampaignRejectedException`), текст уходит в `detail` ProblemDetails как есть
(его показывает UI).

## Правила (знание v1 и решения владельца)

- **Создаёт кампанию только Хранитель по роли** (в v1 — кто угодно). Создатель — участник с ролью
  `Keeper` той же транзакцией; «вступать» в свою кампанию не нужно (в v1 Хранитель не видел свою
  кампанию на главной, пока сам в неё не вступал — отсюда три строки «Хранитель — игрок своей кампании»).
- **Администратор может всё**, включая чужие кампании и журналы (в v1 правил только журнал). В списке
  `/campaigns` он видит все кампании, `MyRole` у чужих — `null`.
- Правка — `ForCampaignAsync`; флаги `CanEdit`/`CanDelete` в списке — `AccessPolicy.ForCampaign(user, role)`
  по уже прочитанной роли, без запроса на строку. Флаги участника — `AccessPolicy.ForMember`.
- **Хранителя не убрать** — ни ему самому, ни админу (409): кампания без Хранителя не живёт. Игрок
  выходит сам или его исключает Хранитель кампании.
- **Выход и исключение не трогают лист**: составной FK `characters (campaign_id, owner_id) →
  campaign_members` с `ON DELETE SET NULL (campaign_id)` оставляет лист у игрока без кампании.
- **Удаление кампании** — `ExecuteDeleteAsync`, остальное делает база: участники, журнал, прохождения и
  брони — каскадом; листы игроков остаются у них, НПС кампании уходят в библиотеку (`SET NULL`).
  В v1 диалог обещал «все игроки и персонажи будут удалены» — это и тогда было неправдой.
- **Псевдоним хранится, только если отличается от имени профиля** (то же правило у переноса T1.3):
  пусто или равно имени — `null`, участник идёт за профилем. Псевдоним с «@» — 400: почту другим не
  показываем. Синхронизация с профилем — галочка в кабинете ([Profile](../Profile/CLAUDE.md), по умолчанию
  выключена): она сбрасывает псевдонимы в `null`, и участник снова идёт за именем профиля.
- **Почт в ответах нет нигде** — `PublicNames.Of(alias, displayName)`: имя, похожее на почту (вход без
  `name` у провайдера заводит имя = почта, как в v1), отдаётся `null`. Тест
  `Emails_never_leave_the_server` ищет «@» во всём ответе.

## Время

Всё время в API — `DateTimeOffset` в UTC (`timestamptz`; в JSON со смещением `+00:00`). В какой пояс
показывать, решает клиент — в вебе это пояс браузера (решение владельца). Сервер ничего не переводит в
«местное» время и не знает пояса пользователя. Дата встречи (`session_date`) — `date`, без пояса.

## Журнал

- **Заметки Хранителя вырезает `JournalService`**, а не разметка: читатель без `CanEdit` получает
  `KeeperNotes = null`. Новое секретное поле встречи — туда же.
- Встреча ссылается на **прохождение этой кампании** (`run_id`); чужое — 400. Уже привязанное при правке
  не перепроверяется (правка заголовка не должна падать). Название сценария — через прохождение.
- `NextNumber` = максимальный номер + 1 (не больше 9999). Номер правится руками, проверка 1…9999.
- Сортировка — по дате встречи, затем по номеру, новые сверху; в памяти: журнал маленький, а EF не
  сортирует по полям record-проекции.
- Ссылки для фазы развития (стр. 92) — активные листы игроков кампании: Хранителю все, игроку свой.
- Пределы (`CampaignLimits`): заголовок 200, хроника и заметки по 20 000 символов. В базе CHECK на длину
  нет — держит сервис, как в v1.

## Главная (`HomeService`)

Один HTTP-запрос, внутри — несколько SQL по одному контексту (последовательно: DbContext не потокобезопасен):

1. мои кампании с ролью, Хранителем и числом игроков;
2. игроки кампаний, которые я веду;
3. листы без документа (`name`/`occupation` — generated-колонки): Хранителю — все листы игроков и НПС его
   кампаний, игроку — только свой активный;
4. доступные: не завершённые, где меня нет, **и ваншоты тоже** (решение владельца: в ваншот вступают и
   участником, и бронью прегена), с `Kind` для бейджа;
5. ваншоты: прохождения с `signup_open` (их видит любой вошедший — бронировать может каждый), прегены
   сценария прохождения кроме архивных, брони с именем забронировавшего.
